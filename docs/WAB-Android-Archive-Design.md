# Локальный архив WhatsApp — решения для форка WAB

Проектная спецификация форка · 26 ноября 2026 г. · Основа: WhatsApp Backup Tools v0.80, коммит `0ad5ff9`.

**Цель первого выпуска** — регулярно снимать с Android-устройства базы двух аккаунтов WhatsApp, общие медиа и адресную книгу. Сохранённые на Mac вложения и аватарки дополняют архив, когда можно установить их принадлежность. Каждый аккаунт открывается в собственном WAB-просмотрщике. Один оператор должен понимать по журналу, что именно удалось забрать с каждого устройства.

## 1. От чего отталкиваемся

WAB v0.80 служит базовой версией для проверки совместимости. При проверке импорта отдельно учитываются обработанные вложения, повторы, отсутствующие файлы и число контактов, для которых удалось определить имя.

Приложение умеет читать исходную базу и искать вложения в нескольких каталогах. При повторном проходе оно может переименовать папку вслед за контактом или группой. Имя отправителя также входит в имена некоторых групповых вложений. Viewer местами показывает `Unknown` из имени папки раньше, чем проверяет известный номер, а вместо профильных фотографий рисует инициалы. Именно эти свойства хотим изменить. Принадлежность снимка конкретному аккаунту устанавливаем по данным и подтверждению оператора, а не по размеру файла.

## 2. Две независимые организации данных

**Источник принадлежит устройству. Рабочий архив принадлежит аккаунту.** Съёмка по USB и обновление WAB — две самостоятельно запускаемые операции. Можно снять очередной снимок и импортировать его позже. Для просмотра уже импортированной переписки телефон не требуется.

Пример целевой раскладки. Угловыми скобками обозначены подставляемые значения. Буквы A и B в примерах обозначают разные постоянные ID.

```text
WhatsApp-Archive/
├── sources/
│   └── <device-label>/
│       ├── device.json
│       ├── media/
│       ├── snapshots/
│       │   ├── <UTC-время>_<account-id-A>/
│       │   │   ├── databases/
│       │   │   ├── key.txt
│       │   │   ├── contacts/
│       │   │   ├── avatars/
│       │   │   └── manifest.json
│       │   └── <UTC-время>_<account-id-B>/    (тот же состав)
│       └── logs/
│           └── <UTC-время-сеанса>.log
└── wab/
    ├── <account-id-A>/
    └── <account-id-B>/
```

- Имя устройства задаёт оператор. Постоянный ID записан в карточке устройства. Для аккаунта назначается постоянный архивный ID. Подтверждённый номер и доступные собственные идентификаторы WhatsApp служат атрибутами для сопоставления. Названия `main`, `second` и номер слота привязаны к прежнему опыту и не входят в новый формат.
- Один завершённый снимок относится к одному устройству, одному аккаунту и одному моменту съёмки. Время в имени папки — UTC, например `2030-01-01T120000Z`. Повтор в ту же секунду получает отдельное имя. Уже завершённые снимки сохраняют своё содержимое.
- `media/` общая для аккаунтов **данного устройства**. В снимке достаточно сослаться на физически сохранённую версию вложения. Отдельная полная копия всего медиакаталога для каждого снимка не требуется.
- Структура на схеме — целевая. Переход с существующих `android-source/` и `wab-main/` проектируем отдельным шагом с проверкой уже рабочих ссылок и количества доступных вложений.

## 3. Съёмка двух аккаунтов на Android

1. Оператор выбирает устройство и первый аккаунт. Скрипт по USB дополняет общий медиакаталог и читает контакты. Одну успешную выгрузку общей адресной книги можно положить в оба снимка этого сеанса. Для каждой копии сохраняется время фактического чтения.
2. Оператор открывает нужный аккаунт в самом WhatsApp и дожидается создания его локальной резервной копии. Скрипт копирует полную базу и доступные относящиеся к ней инкременты под исходными именами. Рядом с базами находится `key.txt` с локально предоставленным ключом этого аккаунта. Привязку ключа к зашифрованной базе проверяем при расшифровке.
3. Оператор переключает аккаунт **в WhatsApp**, создаёт его копию и продолжает тот же сеанс. Скрипт сверяет, какую базу действительно выставил телефон. Если после переключения по старому пути видны те же байты, второй аккаунт не засчитывается как успешно снятый без подтверждения происхождения. Одинаковая база при следующей плановой выгрузке уже подтверждённого аккаунта допустима.
4. На каждый подтверждённый аккаунт создаётся свой снимок, даже когда база не изменилась с прошлого месяца. В нём сохраняются справочник, доступные привязанные аватарки и манифест. Ключи, реальные номера, изображения профилей, базы и пользовательские журналы остаются на локальном диске.
5. Сеанс завершается одним текстовым журналом: устройство, время, ожидаемые и фактически снятые аккаунты, файлы баз и их SHA-256, число записей справочника, количество аватарок, добавленные и пропущенные медиа, конфликты, ошибки и незавершённые шаги. Ключи в журнал не попадают. Обрыв USB не должен превращать частичный снимок в успешный; повтор запуска должен позволять закончить работу без утраты предыдущих данных.

## 4. Правила накопления

| Событие | Результат |
|---|---|
| Новый относительный путь в источнике медиа | Файл добавляется в общий каталог устройства с привязкой к исходному пути. |
| Путь и содержимое уже известны | Существующий файл используется повторно. |
| По прежнему пути пришли другие байты | Обе версии сохраняются. В манифесте или связанном с ним индексе фиксируется, какая версия наблюдалась в данном снимке. |
| Файл исчез с телефона | Предыдущая версия остаётся доступной для старых снимков. |
| Существующий снимок импортировали в WAB повторно | Число сообщений и копий вложений остаётся прежним. Новые подтверждённые сведения могут дополнить индекс. |
| Изменилось имя контакта, отправителя или группы | Обновляется отображаемое имя. Старые папки, имена файлов и ссылки сохраняются. Новые вложения попадают в уже закреплённое место. |
| Изменились только контакты или аватарки | Их можно обновить отдельно. Эта операция не требует пересчитывать хеши всего медиакаталога и повторно копировать фотографии. |

Рабочий архив хранит ссылку на происхождение каждого импортированного сообщения или вложения. Числовой ID строки имеет смысл внутри конкретной исходной базы. Для связи между снимками используем доступные устойчивые ключи WhatsApp в контексте аккаунта и чата. При неоднозначности сохраняем исходные наблюдения до проверки.

## 5. Имена и аватарки

**Снимок отвечает на вопрос «что мы видели в этот раз», карточка WAB — «что нам известно сейчас».** Новое подтверждённое имя становится текущим, прежнее остаётся в истории. Если в свежем справочнике запись отсутствует, пуста или содержит служебную заглушку, сохраняется последнее известное содержательное имя. Для несохранённого контакта порядок отображения таков: последнее известное имя, подтверждённый международный номер с `+`, затем нейтральная подпись. Числовой внутренний LID сам по себе не подтверждает номер телефона.

В первом выпуске источник аватарок — Mac. В снимок конкретного аккаунта попадают доступные изображения с подтверждённой привязкой к контакту или группе. Записываем идентификатор, хеш, источник и время наблюдения. Новая фотография становится текущей, старая остаётся доступна по прежнему снимку. Пустой кэш Mac не стирает известную фотографию. Время наблюдения не позволяет определить точный момент смены аватарки человеком. Для изображения с неизвестным владельцем сохраняем факт обнаружения без назначения контакту. Просмотрщику потребуется поддержка локального изображения и запасной вариант с инициалами.

## 6. Недостающие вложения с Mac

Начинаем с `missing_media_report.csv` конкретного импорта и его `msgstore.db`. Если доступна прежняя карта `attachment-map.tsv`, используем её как кандидата для проверки. Сохраняем результат сверки: аккаунт, снимок, ID сообщения в его базе, исходный Android-путь, файл на Mac, хеш и основание совпадения. Имя файла, дата или совпадение локальных числовых ID на двух устройствах сами по себе недостаточны для автоматической подстановки.

При подтверждённом совпадении и известном Android-пути можно использовать дополнительный медиакаталог WAB. При пустом пути может понадобиться импорт явного соответствия «сообщение → файл». Решение принимаем после подсчёта трёх групп: подтверждено с путём, подтверждено без пути, не сопоставлено. Исходные базы и медиа сохраняем для повторной сверки.

## 7. Приёмка первых изменений

- **Два аккаунта, два сеанса.** В каждом успешном сеансе появляются два самостоятельных снимка, общий медиакаталог пополняется только новыми файлами и версиями. Если оператор не переключил аккаунт, это явно видно в журнале.
- **Смена имени и пропуск в справочнике.** На втором снимке имя изменилось, на третьем отсутствует. Viewer показывает последнее известное имя. Ранее открытая ссылка на групповое фото по-прежнему работает; дополнительной копии из-за смены имени нет.
- **Смена аватарки.** Сделаны снимки с фото A, с фото B и с пустым кэшем. Карточка показывает B, по первому снимку доступна A. Фото одного аккаунта не назначается другому без подтверждённой связи.
- **Конфликт и повтор.** Два файла с одним исходным путём и разными байтами сохраняются раздельно. Повторный импорт того же снимка не создаёт третью копию.
- **Восстановление.** Подтверждённый файл с Mac открывается из нужного сообщения. Для неоднозначного совпадения журнал объясняет, почему связь не установлена.

## 8. Граница работ

Ближайшая разработка — один рабочий форк, один оператор, Android по USB, Mac как дополнительный источник, локальный WAB Viewer. Предлагаемый порядок: съёмка и проверка двух аккаунтов → стабильные пути и отдельное обновление контактов → сверка вложений и показ локальных аватарок. Код, формат и синтетические тесты ведём в GitHub. Собственные выпуски не зависят от принятия PR исходным проектом.

**Отложенная идея.** В дальнейшем источником может стать iPhone. Независимые ID устройств и аккаунтов оставляют такую возможность. Сейчас iPhone-импорт, миграция Android ↔ iPhone и объединение историй разных платформ не входят в реализацию или приёмку.
